# 2. High. TLS Downgrade Attack

## Description
The protocol specification (Section 5.1 and ADR 0002) allows a fallback to TLS 1.2 if TLS 1.3 is unavailable, noting that "Dart's SecurityContext does not expose a minimum protocol version setter". However, allowing TLS 1.2 negotiation introduces the risk of downgrade attacks where an active Man-in-the-Middle (MitM) attacker can alter the handshake messages to force both peers to negotiate TLS 1.2 even if both support TLS 1.3. 
While Section 5.3.4 mitigates the Triple Handshake Attack by requiring the Extended Master Secret (EMS) for TLS 1.2, it does not prevent the downgrade itself. TLS 1.2 lacks some of the robust downgrade protections and forward secrecy guarantees that are mandatory in TLS 1.3. If weak ciphers are accidentally supported or a vulnerability is found in TLS 1.2, the downgrade attack opens the door to exploitation.

## Diagram of the vulnerable design
```mermaid
sequenceDiagram
    participant Device A
    participant MitM Attacker
    participant Device B
    Device A->>MitM Attacker: ClientHello (Supported: TLS 1.3, TLS 1.2)
    Note over MitM Attacker: Attacker modifies ClientHello to remove TLS 1.3
    MitM Attacker->>Device B: ClientHello (Supported: TLS 1.2)
    Device B->>MitM Attacker: ServerHello (Selected: TLS 1.2)
    MitM Attacker->>Device A: ServerHello (Selected: TLS 1.2)
    Note over Device A, Device B: Connection proceeds with TLS 1.2 instead of TLS 1.3
```

## Diagram of the attacker's side
```mermaid
sequenceDiagram
    participant Attacker
    participant Device A
    participant Device B
    Attacker->>Attacker: Intercept traffic between A and B
    Attacker->>Attacker: Drop TLS 1.3 ClientHello, forward modified ClientHello (TLS 1.2 max)
    Attacker->>Attacker: Forward ServerHello (TLS 1.2)
    Note over Attacker: Connection is now TLS 1.2. Attacker can attempt TLS 1.2 specific attacks (e.g., exploiting weak ciphers if misconfigured).
```

## The fix
If TLS 1.3 minimum enforcement is impossible via Dart's API, the protocol must implement application-layer downgrade detection. 
In the `session.hello` message (the first encrypted message), peers should exchange the highest TLS version they actually support. If a peer receives `session.hello` over a TLS 1.2 connection, but the `session.hello` payload indicates the sender supports TLS 1.3, it proves a downgrade attack occurred. The connection MUST be immediately terminated with `ProtocolError` or `AuthenticationFailed`.

## Diagram of the fixed design
```mermaid
sequenceDiagram
    participant Device A
    participant MitM Attacker
    participant Device B
    Device A->>MitM Attacker: ClientHello (TLS 1.3, TLS 1.2)
    MitM Attacker->>Device B: ClientHello (TLS 1.2)
    Device B->>MitM Attacker: ServerHello (TLS 1.2)
    MitM Attacker->>Device A: ServerHello (TLS 1.2)
    Device A->>Device B: session.hello (Payload: highest_tls_supported = 1.3)
    Note over Device B: Device B sees connection is TLS 1.2, but payload says A supports TLS 1.3
    Device B-->>Device A: session.reject (Downgrade detected)
    Device B->>Device B: Terminate connection
```

## Diagram of the attacker's side with the new design
```mermaid
sequenceDiagram
    participant Attacker
    participant Device A
    participant Device B
    Attacker->>Attacker: Intercept and modify ClientHello to force TLS 1.2
    Attacker->>Device B: ClientHello (TLS 1.2)
    Device B->>Device A: ServerHello (TLS 1.2)
    Device A->>Device B: session.hello (highest_tls_supported = 1.3) over TLS 1.2
    Note over Attacker: Attacker cannot modify the encrypted session.hello payload.
    Device B->>Device B: Detects mismatch, drops connection.
    Note over Attacker: Attack fails.
```
