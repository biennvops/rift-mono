I've reviewed the skeleton and it looks like a solid starting point for the Windows daemon. I have a few findings to address before we move forward:

### 1. Deprecated BouncyCastle Package
In `Rift.Daemon.Windows.csproj`, you are referencing `Portable.BouncyCastle` `1.9.0`. This package has been deprecated. The official package was renamed to `BouncyCastle.Cryptography` starting with version 2.0. Please update the package reference.

### 2. Redundant loop in `Worker.cs`
`ipcListener.ListenAsync(stoppingToken)` contains its own `while (!stoppingToken.IsCancellationRequested)` loop. The `while` loop with `Task.Delay(10000)` inside `Worker.ExecuteAsync` is entirely redundant. You can simplify `Worker.cs` to just:
```csharp
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    logger.LogInformation("Rift Daemon (Windows) starting...");
    await ipcListener.ListenAsync(stoppingToken);
}
```

### 3. Graceful shutdown in `HandleClientAsync`
In `IpcListener.cs`, `HandleClientAsync` takes `stoppingToken` but doesn't actually use it. `await jsonRpc.Completion;` will block indefinitely until the client disconnects. If the Windows Service needs to shut down cleanly, you should tie the `stoppingToken` to the RPC session so it can tear down the connection when the service is stopping. For example, by registering a callback:
```csharp
using var registration = stoppingToken.Register(() => pipe.Dispose());
```
or by manually disposing `jsonRpc` when the token is cancelled.

### 4. Missing cancellation on `WaitForConnectionAsync`
`WaitForConnectionAsync` takes the `stoppingToken`, which is good. But consider configuring `pipeOptions` with `PipeOptions.Asynchronous` (which you did) and ensuring that the pipe is properly disposed if `WaitForConnectionAsync` throws `OperationCanceledException`. Wait, you are disposing the pipe on exception? Actually, you don't dispose `pipeServer` in the catch block inside the loop unless `HandleClientAsync` fails to spawn. Wait, if `WaitForConnectionAsync` throws `OperationCanceledException`, the loop breaks, but `pipeServer` is never disposed! You should put the `pipeServer` inside a `using` declaration or a `try/finally` block inside the loop so it's disposed on cancellation.

Otherwise, the IPC setup with ACLs and `StreamJsonRpc` looks well-structured and aligns with the cross-process architecture.
